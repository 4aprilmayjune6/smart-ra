MCP 개정분 기준 총평은 **[조건부 적절]**입니다. MCP를 “에이전트-도구 경계”로 한정하고, REST/웹콘솔과 서비스 계층을 공유하도록 한 방향은 적절합니다. 다만 계약 요구사항으로는 인증·도구 스키마·감사증적·간접 프롬프트 주입 대응의 세부가 아직 부족합니다.

1. [심각도: 높음] **승인 통제는 좋지만, 승인 전 상태변경 통제가 더 필요합니다.**  
`update_memo_section`, `submit_memo_for_approval`, `export_memo`는 승인 자체는 아니지만 조서 후보물과 외부 반출물을 바꾸는 고위험 도구입니다.  
개선: 섹션 수정 전후 diff, 작성 주체(사용자/에이전트), 근거 검증 결과, 버전 잠금, 제출 후 수정 금지 또는 재제출 절차를 명시하세요. `export_memo`는 승인본/초안 워터마크와 반출 권한을 분리해야 합니다.

2. [심각도: 높음] **MCP 클라이언트 신뢰성 통제가 선언 수준입니다.**  
“법인 승인 MCP 클라이언트”라고 되어 있으나 기술적으로 미승인 클라이언트·개인 토큰 재사용·클라이언트 위장 차단 방식이 불명확합니다.  
개선: 클라이언트 allowlist, client_id별 정책, 토큰 audience/scope, mTLS 또는 사내 프록시 경유, 세션별 사용자 동의/재인증 조건을 NFR-MCP-02 또는 IR-06에 추가하세요.

3. [심각도: 높음] **간접 프롬프트 주입 대응이 라벨링 중심입니다.**  
비신뢰 라벨과 지시문 삽입 금지는 필요하지만, 다른 MCP 도구(K-IFRS 검색 등)와 같은 에이전트 세션에서 조합될 때 교차 오염 위험이 남습니다.  
개선: “도구 결과는 명령이 아니라 데이터”라는 클라이언트 가드 프롬프트, untrusted 리소스의 쓰기 도구 인자 직접 전파 금지, 쓰기 도구 호출 전 서버측 정책검사, 오염된 외부 텍스트 기반 `update_memo_section` 차단 테스트를 구체화하세요.

4. [심각도: 중간] **도구 카탈로그는 적절하나 스키마 품질 요구가 부족합니다.**  
15개 도구 목록은 업무 흐름을 대체로 커버하지만 예시는 `get_risk_signals` 1개뿐입니다. 에러 모델, pagination cursor, idempotency key, job 상태 enum, 리소스 만료/권한 오류가 정의되지 않았습니다.  
개선: 15개 전 도구에 JSON Schema, 공통 오류 코드, 권한 scope, read/write annotation, idempotency, 감사로그 필드를 요구하세요.

5. [심각도: 중간] **`run_cross_validation`의 “조회(멱등 실행)” 표현이 모호합니다.**  
결과를 새로 계산·저장한다면 상태변경이고, 단순 계산이면 캐시/버전 기준이 필요합니다.  
개선: `preview_cross_validation`과 `persist_cross_validation_result`처럼 분리하거나, 멱등 실행의 저장 여부·룰 버전·스냅샷 기준을 명시하세요.

6. [심각도: 중간] **감사로그가 조서 증적으로 쓰기엔 항목이 부족합니다.**  
현재는 사용자·도구·입력 해시·응답 요약·시각 중심입니다. 실제 감리 대응에는 “무엇을 근거로 어떤 버전이 어떤 결과를 냈는지”가 더 필요합니다.  
개선: client_id, IP/망, engagement_id, resource URI, schema/protocol version, ruleset version, snapshot id, 권한판정 결과, 실패 로그, append-only hash chain을 포함하세요.

7. [심각도: 중간] **job 패턴이 수집 중심으로만 보입니다.**  
`refresh_company_data`는 명확하지만 export, 재분석, 대량 메모 생성, 파싱 재처리도 장기 작업이 될 수 있습니다.  
개선: 범용 `get_job_status`, job type enum, retry/cancel, partial success, 재처리 큐, job별 감사로그 연결을 정의하세요.

8. [심각도: 중간] **NFR-MCP-04의 동시 세션 `[M]개`가 미정입니다.**  
성능·라이선스·인프라 산정이 어려워집니다.  
개선: PoC/MVP/운영 단계별 동시 사용자와 세션 수, 도구별 rate limit, 사용자별 throttling 기준을 수치화하세요.

9. [심각도: 낮음] **MCP 적합성 검수는 방향은 좋지만 범위가 좁습니다.**  
표준 클라이언트 2종 연결 시연만으로는 장기 호환성을 보장하기 어렵습니다.  
개선: MCP contract test suite, schema backward compatibility test, negative auth test, 프롬프트 주입 red-team 시나리오, 대용량 resource URI 테스트를 검수 항목에 추가하세요.

10. [심각도: 낮음] **프롬프트 카탈로그의 거버넌스가 약합니다.**  
`risk-assessment-review`, `memo-narrative`는 감사 품질에 영향을 주지만 승인·버전·변경관리 요구가 없습니다.  
개선: 프롬프트 버전 고정, SME/정보보호 승인, 변경 이력, 테스트 케이스, 금지 문구를 부록 D 또는 NFR-MCP에 포함하세요.

최종 등급: **[조건부 적절]**.  
MCP 채택 자체와 판정·서술 분리, 웹 콘솔 승인 전용, REST와 서비스 계층 공유는 설계 방향이 좋습니다. 조건은 클라이언트 신뢰, 전 도구 스키마, 쓰기 도구 통제, 프롬프트 주입 방어, 조서 수준 감사증적을 계약 검수 가능한 수준으로 더 구체화하는 것입니다.
