제안요청서(RFP)

DART 공시 기반 감사 위험평가 자동화 플랫폼 (가칭 "SMART-RA") 구축 사업

항목 내용
문서 버전 v1.2 (초안 — 구현·제공 방식을 MCP 기반으로 개정(3.5장·4.6장·부록 D), 외부 AI 교차검토 반영(부록 C))
작성일 2026-07-04
발주기관 [회계법인명] 품질관리실 / 감사혁신팀 (발주 주체에 맞게 수정)
사업 유형 소프트웨어 개발 용역 (단계별 계약: PoC → MVP → 확산)

문의처 [담당자 성명 / 이메일 / 연락처]

본 문서는 ① DART 공시 위험시그널 추출, ② 산업별 위험매핑, ③ 계속기업 불확실성 스코어링, ④ 위험평가 메모 자동생성의 4개 모듈과 기존 전표분석(JET) 모듈 연동 인터페이스를 구축하기 위한 제안요청서이다. 제안사는 본 문서의 요구사항을 기준으로 제안서를 작성하되, 더 나은 대안이 있는 경우 근거와 함께 대안을 제시할 수 있다.

1. 사업 개요

1.1 추진 배경

  1. 위험기반 감사 요구의 상승 — 신외부감사법 체제(주기적 지정제, 표준감사시간, 내부회계관리제도 감사) 이후 감사계획 단계의 위험식별·평가 품질이 감사품질을 좌우하는 핵심 요인이 되었다.
  2. 개정 감사기준서 315 — 개정 KSA 315는 위험평가절차를 체계화하면서 자동화된 도구와 기법(ATT, Automated Tools and Techniques) 의 활용을 명시적으로 인정한다. 공시·재무 데이터에 기반한 자동화된 위험식별은 기준서가 예정하는 활용 형태에 부합한다.
  3. 수작업 검토의 한계 — 현재 감사팀은 DART를 수작업으로 검색하여 공시를 검토하고 엑셀 체크리스트로 위험을 정리한다. 검토 범위·깊이가 개인 역량에 의존하고, 전기 KAM·정정공시·특수관계자 거래 등 반복적 확인 항목이 누락되기 쉽다.
  4. 품질관리기준(ISQM 1) 대응 — 법인 차원의 기술적 자원(technological resources) 관리 정책 아래, 검증되고 버전관리되는 표준 도구를 제공할 필요가 있다.

1.2 사업 목적

  1. 감사 수임평가 및 감사계획 단계의 위험식별·평가 절차를 자동화·표준화한다.
  2. 공시(모듈1)·산업(모듈2)·재무(모듈3)의 세 관점 신호를 교차검증하여 핵심위험을 도출하고, 이를 경영진 주장과 후속 감사절차로 번역한 위험평가 메모 초안을 자동 생성한다(모듈4).
  3. 식별된 위험을 기존 전표분석(JET) 모듈의 룰 가중치로 자동 연동하여 KSA 315(위험평가) → KSA 240(부정위험 대응, 분개테스트) 흐름("315→240 흐름")의 추적성을 확보한다.
  4. 모든 산출물에 근거(원문 공시 링크)와 재현성(버전·스냅샷) 을 부여하여 감사조서 편철과 감리 대응이 가능한 수준의 증적을 남긴다.

1.3 사업 범위

구분 내용
포함 모듈 1~4 개발 및 MCP 서버로의 제공(도구·리소스·프롬프트 — 3.5장·부록 D), 공통 기반(수집 파이프라인·저장소·인증·권한·감사로그), 관리·승인 웹 콘솔(대시보드·메모 승인·이력 — 일상 업무는 에이전트 경유), JET 모듈 연동 인터페이스, 초기 8개 산업 위험맵 콘텐츠(발주사 SME 검수 전제), 운영 이관·교육
제외 전표분석(JET) 모듈 자체의 개발·수정, 감사조서 시스템과의 양방향 통합(내보내기만 포함), 비상장·유한회사 전용 수집 체계(옵션 제안 가능), 그룹 연결실체 간 위험 전파 분석(향후 과제)

1.4 기대효과

  • 감사계획 단계 공시검토 시간 단축(회사당 수 시간 → 수 분) 및 검토 범위의 전수화(全數化)
  • 위험식별의 법인 표준화 → 팀 간 품질 편차 축소, 신입 인력의 조기 전력화
  • 315→240→JET로 이어지는 위험 대응의 추적가능한 문서화 → 감리·품질관리 검토 대응력 강화
  • 수임 전 위험평가(client acceptance)에 동일 엔진 재사용

2. 현황·전제·제약

2.1 현황(As-Is)

  • 공시검토: 감사팀원이 DART 웹에서 회사별 공시를 수작업 열람, 위험 항목을 엑셀로 정리
  • 산업위험: 팀별로 상이한 체크리스트, 산업 전문 지식이 문서화·공유되지 않음
  • 계속기업: 재무비율을 개별 계산, 판단 기준 불일치
  • JET: 전표분석 모듈은 존재하나 위험평가 결과와 룰 가중치가 수동으로 연결됨

2.2 전제조건

  1. 발주사는 OpenDART 인증키를 확보·제공한다(무료 발급, 키 관리 정책은 NFR-SEC 참조).
  2. 발주사는 JET 모듈의 룰 식별체계(rule_id)와 가중치 반영 방식을 제공하고 연동 API 협의에 참여한다.
  3. 산업 위험맵 콘텐츠(모듈2)의 감사 전문 내용은 발주사 SME(회계사)가 검수한다. 제안사는 스키마·도구·초안 작성을 담당한다.
  4. 시스템 사용 대상: 감사본부 소속 임직원(초기 약 [N]명, 동시접속 [M]명 수준).
  5. MCP 클라이언트 환경: 법인의 LLM 이용 정책상 승인된 MCP 클라이언트(예: Claude Desktop·Claude Code 사내 배포 또는 자체 에이전트)와 데이터 반출 통제(공급자 미학습 계약 등, NFR-SEC-06)가 확보되어야 한다. 미승인 조직·기간에도 REST API·웹 콘솔 경로로 전 기능 사용이 가능해야 한다(SFR-607).

2.3 제약사항

  1. 공개데이터 한계 — DART 공시가 없는 비상장 소규모·유한회사는 커버리지가 제한적이다(감사보고서 공시 범위 내에서만 가능하다). 재무제표 API는 2015년 이후 정기보고서 기준이다.
  2. API 쿼터 — OpenDART는 인증키당 일일 호출 한도(현행 20,000건 수준, 정책 변동 가능)가 있으므로 증분수집·캐시 설계가 필수다. 복수 키 우회는 이용약관 검토 전까지 금지한다.
  3. 비정형 원문 — 감사보고서·주석(특수관계자, KAM 등)은 구조가 표준화되어 있지 않아 파싱에 실패할 가능성이 상존한다. 파싱에 실패하더라도 이를 은폐하지 않고 "수동확인 필요" 항목으로 명시적으로 전환해야 한다.
  4. 판단 대체 금지 원칙 — 본 시스템은 의사결정 지원 도구이며, 위험평가의 최종 판단은 감사인이 수행한다. 모든 산출물에는 면책 문구를 강제로 삽입한다(SFR-405).

2.4 시스템 산출물의 위상 (감사기준 관점)

  • 시스템 산출물은 그 자체로 감사증거가 아니라 감사인이 이용하는 정보이다. 감사인은 KSA 500에 따라 정보의 목적적합성·신뢰성을 평가한 후 활용한다. 이를 위해 시스템은 (i) 원천 데이터의 출처·수집시각·해시, (ii) 판단 규칙의 버전, (iii) 산출 시점의 입력 스냅샷을 항상 함께 제공해야 한다(재현성, NFR-REL).
  • 승인된 위험평가 메모와 근거 패키지는 감사조서로 편철될 수 있어야 하며, 외부감사법상 감사조서 보존기간(8년)과 정합하는 보존 정책을 따른다(NFR-CMP).

3.5 MCP 인터페이스 설계 (구현·제공 방식) ★

본 시스템의 4개 모듈은 MCP(Model Context Protocol) 서버로 구현·제공한다. 감사인은 법인이 승인한 에이전트(Claude Desktop·Claude Code 사내 배포, 자체 에이전트 앱 등 MCP 클라이언트)에서 자연어로 위험평가 업무를 수행하고, 에이전트가 MCP 도구를 호출한다. 상세 도구·리소스·프롬프트 카탈로그는 부록 D.

설계 원칙

  1. 판정은 서버, 서술은 에이전트 — 신호 산출·스코어링·핵심위험 도출(교차검증 룰)·메모 초안 생성은 전량 서버측 결정론 엔진이 수행한다. 에이전트(LLM)는 조회·오케스트레이션·서술 보완만 담당하며, 위험 판정을 생성·변경할 수 없다(SFR-602). 설명가능성 원칙(8.1)은 MCP 전환 후에도 동일하게 유지된다.
  2. 모든 도구 응답에 근거 포함 — signal_id·rcept_no·룰 버전 메타를 응답에 포함하여, 에이전트가 근거 없는 서술을 생성할 수 없는 구조를 만든다.
  3. 쓰기 도구 최소화, 승인은 사람 — 상태 변경 도구는 최소 집합으로 한정하고 전건 서버측 검증을 거친다. 메모 승인은 MCP 도구로 제공하지 않으며 웹 콘솔에서 업무수행이사가 수행한다(SFR-604) — 에이전트 자동 승인의 구조적 차단.
  4. 장기 작업은 job 패턴 — 수집·재분석은 job_id 반환 후 상태 조회 도구로 확인한다(동기 도구 응답 p95 ≤ 10초, NFR-MCP-04).
  5. 토큰 예산·신뢰경계 — 대용량 데이터는 리소스 URI로 제공하고, 공시 원문 등 외부 유래 텍스트는 비신뢰(untrusted) 라벨을 부착해 반환한다(간접 프롬프트 주입 대응, SFR-606).

전송·인증: 운영은 사내망 Streamable HTTP + OAuth 2.1(사내 IdP/OIDC 연계, per-user 토큰). 에이전트는 사용자 권한을 초과할 수 없으며 NFR-SEC-02의 인게이지먼트 격리(RLS)가 그대로 적용된다. 개발·PoC는 stdio. 프로토콜·도구 스키마는 semver로 버전관리한다(NFR-MCP-01). 세부 사양은 구현 착수 시점의 최신 MCP 사양 기준으로 확정하고 계약 테스트로 고정한다.

서버 간 연동과의 구분: MCP는 "에이전트 ↔ 도구" 경계의 프로토콜이다. JET 가중치 반영(IR-02)·조서 내보내기 등 서버 ↔ 서버 연동은 MCP 대상이 아니며 REST/이벤트 방식을 유지한다.

기대 시너지: 법인이 사용하는 다른 MCP 도구(예: K-IFRS 기준서·질의회신·감리지적사례 검색 서버)와 동일 에이전트 세션에서 조합되어, "핵심위험 → 관련 기준서 → 유사 감리지적사례"를 하나의 대화 흐름에서 교차 검토할 수 있다.

  • 전송: 운영 Streamable HTTP(사내망, TLS) / 개발 stdio. 인증: OAuth 2.1(사내 IdP 연계, per-user 토큰).
  • 제공 대상: 법인 승인 MCP 클라이언트(Claude Desktop·Claude Code 사내 배포, 자체 에이전트 등 표준 준수 클라이언트).

IR-07 외부정보 소스 (기사·감리지적사례) (v1.3 신설)

8. 기술스택 상세

8.1 선정 원칙

  1. 설명가능성 우선 — 위험 판정은 감리·품질관리 검토에서 "왜"를 설명할 수 있어야 한다. 따라서 판정 로직은 블랙박스 ML이 아닌 선언적 룰 + 공개 산식을 기본으로 하고, ML은 Phase 3에서 화이트박스(계수 공개형) 보정에 한정한다.
  2. 공식 API 사양 우선 — 핵심 수집 경로의 계약 기준은 공식 OpenDART REST 사양이며, 계약 테스트(contract test)도 공식 사양을 대상으로 한다. OpenDartReader·dart-fss는 개발 편의 보조 레이어로 한정하고, 얇은 어댑터 계층 뒤에 배치하여 직접 REST 폴백 경로를 항상 유지한다(커뮤니티 유지 중단 리스크 격리).
  3. 온프레미스 배포 가능성 — 전 구성요소는 오픈소스 또는 자체 호스팅 가능해야 한다.
  4. 단계적 복잡도 — 파일럿(Compose·APScheduler·Streamlit)에서 확산(K8s·Airflow·React)으로 필요 시점에만 승격한다.

8.3 주요 선정 근거와 대안 비교

8.3.1 저장소: PostgreSQL(+JSONB) vs MongoDB

  • 신호·산업맵은 반정형이지만, 인게이지먼트·권한·감사로그·메모 워크플로는 강한 정합성(트랜잭션·조인)이 필요하다. PostgreSQL JSONB가 반정형을 흡수하면서 정합성을 보장하므로 단일 PostgreSQL로 운영 복잡도를 낮춘다. MongoDB는 조인·트랜잭션 요건과 운영 인력 측면에서 배제.
  • 분석 가속·백테스트 탐색용으로 DuckDB를 보조 채택 가능(선택).

8.3.2 오케스트레이션: APScheduler → Airflow (Prefect 대안)

기준 APScheduler Airflow 2.x Prefect 2
복잡도 매우 낮음(프로세스 내장) 높음(별도 인프라) 중간
백필·재처리 수동 구현 내장(DAG 백필) 내장
모니터링 UI 없음 성숙 성숙
국내 운영 레퍼런스 — 풍부 성장 중

→ 파일럿은 APScheduler로 충분(회사 수 수십 개). 전환 트리거(예시): 등록 회사 200개사 초과, 파이프라인 DAG 10개 초과, 월 수동 재처리 4회 초과, 전담 운영 인력 배정 — 중 2개 이상 충족 시 Phase 2 착수 시점에 Airflow/Prefect 중 택1을 확정한다. Prefect는 온프레미스 운영성 관점에서 동급 대안으로 인정.

8.3.3 판정 로직: 룰 기반 vs ML

  • 감리 대응 관점에서 "이 회사가 왜 🔴인가"에 대해 산식과 임계값으로 답할 수 있어야 한다. 초기 릴리스는 전량 룰·산식 기반(부록 B), 오탐 피드백(SFR-110)을 축적한 후 Phase 3에서 로지스틱 회귀 등 계수 공개형 모델로 가중치를 보정한다(모델도 버전관리·백테스트 필수).

8.3.4 LLM 활용 범위와 통제 (선택 기능)

  • 사용처 한정: ① KAM·특수관계자 주석 등 비정형 텍스트의 구조화 추출 보조(SFR-107, 서버측), ② 메모 서술 다듬기(SFR-404), ③ MCP 에이전트로서의 조회 오케스트레이션·대화형 서술 보완(3.5장·4.6장 — 클라이언트측). 어느 경로든 위험 판정·점수 산출에는 LLM을 사용하지 않는다(SFR-602).
  • 통제: 공개정보만 전송(NFR-SEC-06) · temperature 0 · 구조화 출력(JSON 스키마 강제) · 모든 서술 문장에 signal_id 인용 강제 + 후처리 검증기(인용 없는 문장 제거) · 프롬프트/응답 전건 로깅 · 모델 버전 고정과 회귀 평가셋 운영.
  • 모델: 특정 모델명을 계약에 고정하지 않고 요건 중심으로 명세한다 — 구조화 출력(JSON Schema 강제), 근거 인용 준수, 데이터 미학습(zero retention) 계약, 버전 고정(pin)·회귀 평가 가능성. 계약 시점 사용 가능한 승인 모델 중 선정한다(2026-07 기준 예시: Anthropic Claude 계열 — 구조화 추출·초안 서술 claude-sonnet-5, 복잡 사례 claude-fable-5). 법인 정책상 외부 API 불가 시 순수 템플릿 모드로 전 기능 동작(성능 저하 없는 기본 경로).

8.3.5 프런트엔드 단계론

  • 파일럿(Phase 0~1)의 목적은 룰·콘텐츠 검증이므로 Streamlit으로 화면 개발 비용을 최소화하되, 승인 워크플로가 들어가는 Phase 2부터는 React/Next.js 전환을 필수로 한다(Streamlit은 다단계 승인·변경추적·동시 편집에 구조적 한계). 이관을 전제로 백엔드는 처음부터 REST API(FastAPI)로 분리 설계한다.

8.3.6 한국어 텍스트 처리

  • 키워드 매칭은 단순 문자열 매칭 시 활용형·복합어("횡령혐의", "배임수재")를 놓치므로 형태소 분석기(kiwipiepy)로 표제어 기반 매칭을 수행하고, "해당사항 없음"류 부정 문맥을 제외 규칙으로 처리한다. 사전·제외 규칙은 관리자 UI(SFR-109)로 운영한다.

8.3.7 제공 방식: 왜 MCP인가

기준 REST API + 웹 UI 단독 MCP 서버 (채택)
감사인 상호작용 화면 조작 중심, 기능별 화면 개발 필요 에이전트 대화로 조회→분석→메모 서술까지 수행. 웹 콘솔은 관리·승인에 집중
타 도구와의 조합 개별 통합 개발 필요 개방형 표준 — 기준서 검색·감리사례 등 법인 보유 MCP 도구와 즉시 조합
클라이언트 종속성 자체 UI에 종속 표준 준수 클라이언트 간 교체 가능(Claude Desktop/Code, 자체 에이전트 등)
LLM 통제 별도 설계 필요 판정·서술 분리(SFR-602), 근거 강제, 쓰기 통제(SFR-604), 신뢰경계(SFR-606)를 프로토콜 경계에서 일괄 적용
  • REST API를 폐기하는 것이 아니다 — MCP 서버·REST API·웹 콘솔이 동일한 내부 서비스 계층을 공유하며(SFR-607), MCP 서버는 그 위의 도구 어댑터다. 따라서 MCP 채택이 백엔드 스택(8.2) 선정을 바꾸지 않는다.
  • 구현은 공식 Python MCP SDK 또는 FastMCP 2.x를 사용하고, 전송·인증 세부(Streamable HTTP, OAuth 2.1)는 구현 착수 시점의 최신 MCP 사양으로 확정한다(IR-06).
