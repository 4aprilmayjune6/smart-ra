파일은 수정하지 않고 검토했습니다. 총평 등급은 **[조건부 적절]**입니다. 방향성은 감사 위험평가 자동화 목적에 대체로 맞지만, 검수 기준·데이터 신뢰성·보안통제·운영 아키텍처가 더 구체화되지 않으면 실제 감사조서/감리 대응 수준으로 쓰기엔 위험합니다.

**1. SFR 누락·과잉·모호**
- [심각도: 높음] **파싱 실패/부분 추출의 업무 처리 기준이 부족함.** “수동확인 필요”는 있으나 SLA, 담당자 배정, 승인 전 차단 여부, 메모 반영 방식이 불명확합니다.  
  개선: 파싱 실패 유형별 `blocking / warning / informational` 등급, 담당자 태스크, 승인 전 필수 해소 조건을 SFR로 추가하세요.

- [심각도: 높음] **모듈4 핵심위험 도출 룰의 품질 기준이 모호함.** 기본 룰셋 20개 이상은 수량 기준일 뿐, 감사기준서·계정·주장·절차 매핑의 정확성 기준이 약합니다.  
  개선: 룰별 필수 필드, SME 승인 절차, 룰 단위 테스트, false positive/false negative 검토표를 수용기준에 넣으세요.

- [심각도: 중간] **산업 위험맵 8개 산업 범위가 과함.** 금융을 은행/여신/보험으로 분리하면서도 10~12개월 일정에 포함해 콘텐츠 품질 저하 가능성이 큽니다.  
  개선: Phase 2는 4~5개 핵심 산업으로 축소하고, 나머지는 별도 콘텐츠 구축 트랙으로 분리하는 편이 현실적입니다.

- [심각도: 중간] **JET 연동은 “가중치 조정 이벤트”만 있고 되돌리기·충돌·승인 취소 흐름이 부족합니다.** 승인본 잠금은 있으나 JET에 이미 반영된 룰 변경의 rollback이 정의되지 않았습니다.  
  개선: `RISK_WEIGHT_UPDATE`, `REVOKE`, `SUPERSEDE` 이벤트, 멱등키, 적용 상태 조회 API, 수동 재처리 절차를 추가하세요.

- [심각도: 중간] **색상/등급 체계가 문서 일부에서 깨져 있고 RED/YELLOW/GREEN 의미가 일관되지 않습니다.** 모듈1은 RED/YELLOW, 모듈3은 GREEN 포함인데 메모·백테스트 기준에는 기호가 깨져 있습니다.  
  개선: `severity`, `confidence`, `impact`, `review_status`를 분리해 정의하세요. 위험도와 신뢰도를 한 필드에 섞으면 운영 중 오해가 생깁니다.

**2. NFR 적정성**
- [심각도: 높음] **보안 요구가 기본 수준에 머뭅니다.** RBAC, TLS, 암호화는 있으나 감사법인 환경에서 필요한 세부 통제가 부족합니다.  
  개선: 인게이지먼트별 row-level security, 관리자 권한 이중승인, break-glass 접근, 데이터 반출 통제, 다운로드 워터마크, 세션 타임아웃, IP/망 접근 제한을 명시하세요.

- [심각도: 높음] **LLM 통제는 방향은 맞지만 “공개정보만 전송”으로 충분하지 않습니다.** 공개 공시라도 감사팀의 선택·조합·메모 문맥은 감사계획 정보가 될 수 있습니다.  
  개선: 외부 LLM 기본 비활성화, 프롬프트 내 내부 메타 제거, DLP 필터, 프록시 승인 정책, 공급자 데이터 미학습 계약, 국내/전용 엔드포인트 조건을 NFR에 넣으세요.

- [심각도: 중간] **재현성 100%는 LLM 포함 시 과도하거나 검증 불가능합니다.** 모델 버전 고정과 temperature 0만으로 장기 동일 출력을 보장하기 어렵습니다.  
  개선: 감사조서 편철 기본본은 템플릿 모드만 허용하고, LLM 출력은 “비편철 보조 초안” 또는 검증 후 템플릿 산출물에 흡수하는 구조로 제한하세요.

- [심각도: 중간] **컴플라이언스 범위가 감사기준 중심이고 개인정보/정보보호 법령 매핑이 약합니다.**  
  개선: 개인정보보호법, 신용정보/내부정보 처리 정책, 외부위탁 보안점검, 로그 보존·파기 정책, 오픈소스 SBOM/CVE 패치 SLA를 추가하세요.

- [심각도: 낮음] **가용성 99.5%는 배치성 시스템에는 높게 보일 수 있으나 RTO/RPO가 없습니다.**  
  개선: 업무시간 RTO 4시간, RPO 24시간 등 복구 기준을 별도 정의하세요.

**3. 기술스택**
- [심각도: 중간] **Python/FastAPI/PostgreSQL 선택은 적절합니다.** 룰 기반·데이터 파이프라인·감사 추적성 요구와 잘 맞습니다. PostgreSQL+JSONB도 정합성과 반정형 데이터를 같이 다루기 좋습니다.

- [심각도: 높음] **OpenDartReader/dart-fss 의존은 보조 수단이어야 합니다.** RFP가 어댑터와 REST 폴백을 언급한 것은 좋지만, 실제 계약상 “공식 OpenDART REST 기준”을 우선으로 못 박아야 합니다.  
  개선: 커뮤니티 라이브러리는 개발 편의 레이어로만 두고, 핵심 수집은 공식 API 스펙 기반 contract test로 검증하세요.

- [심각도: 중간] **APScheduler → Airflow 단계론은 타당하나 전환 기준이 모호합니다.**  
  개선: 대상 회사 수, DAG 수, 재처리 빈도, 운영자 수 기준을 정해 `Phase 2부터 Airflow/Prefect 중 택1`로 명확화하세요. Prefect도 온프레미스 운영성이 좋아 대안으로 유효합니다.

- [심각도: 중간] **Streamlit → React 전환은 PoC에는 좋지만 MVP에 승인 워크플로가 들어가면 Streamlit은 빨리 한계가 옵니다.**  
  개선: PoC만 Streamlit, MVP부터 React/Next.js 또는 최소한 별도 프론트로 가는 편이 낫습니다.

- [심각도: 높음] **Anthropic 모델명이 문서상 미래/가정 모델처럼 보이며 조달 리스크가 있습니다.**  
  개선: 특정 모델명 고정보다 “제안 시점 사용 가능한 승인 모델, JSON schema/근거 인용/데이터 미학습 계약 충족”으로 요구하세요.

**4. 아키텍처·데이터 파이프라인 실행 리스크**
- [심각도: 높음] **DART API 한도와 원문 구조 변동이 핵심 리스크입니다.** 200개사 야간 배치와 1,000개사 확장은 가능하더라도 원문 ZIP/XML 파싱 실패율이 병목이 됩니다.  
  개선: 원문 파서별 성공률 대시보드, API 응답 캐시, 재처리 큐, endpoint별 fallback, 샘플 코퍼스 기반 회귀테스트를 필수화하세요.

- [심각도: 높음] **백테스트 설계가 약합니다.** 의견거절·감리지적·상장폐지 30개사와 정상 30개사는 표본이 작고 selection bias가 큽니다.  
  개선: 산업/규모/연도별 층화 표본, 사건 발생 전 시점 고정, 생존편향 제거, 룰별 기여도 리포트, precision/recall/F1을 별도 산출하세요.

- [심각도: 중간] **계속기업 스코어링은 금융업·지주회사·바이오·플랫폼 기업에서 왜곡 가능성이 큽니다.** 문서에 금융업 제외/별도 지표셋은 있으나 다른 산업 특성 반영이 약합니다.  
  개선: 산업별 지표셋, 하드룰 우선순위, 수익 전 단계 기업용 지표, 현금 runway, 차입 만기구조 등 보완 지표를 추가하세요.

- [심각도: 중간] **감사인 변경, KAM, 특수관계자 추출은 문서 양식 변화에 취약합니다.**  
  개선: 정규식만이 아니라 섹션 탐지, 표 구조 파싱, LLM 보조 추출의 검증 라벨, 수동 교정 데이터 축적 루프를 설계하세요.

- [심각도: 낮음] **문서 자체에 `?` 깨진 문자들이 남아 있습니다.** 등급/화살표/표현이 일부 훼손되어 계약 해석 리스크가 있습니다.  
  개선: 최종 RFP 배포 전 UTF-8 정합성, RED/YELLOW/GREEN 표기, 특수문자 전체 정리를 하세요.

**5. 총평**
**[조건부 적절]**입니다. 감사기준서 315→240→570 흐름, 근거 링크, 룰 버전, 스냅샷, 템플릿 우선, LLM 제한이라는 기본 설계 방향은 적절합니다. 다만 현 상태는 “좋은 PoC/RFP 초안”에 가깝고, 실제 감사조서 편철·감리 대응 시스템으로 쓰려면 **파싱 실패 처리, 룰 검증, LLM/보안 통제, JET rollback, 백테스트 방법론**을 계약 요구사항 수준으로 더 구체화해야 합니다.
